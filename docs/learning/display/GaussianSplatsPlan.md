# Native Gaussian splats implementation plan

Implement an opt-in preview in iTwin.js's WebGL2 renderer. Load Gaussian splats through the existing reality-model and 3D Tiles pipeline, preserving compatibility with CesiumJS and Cesium ion data without using Cesium's renderer.

## Compatibility and scope

- Accept glTF 2.0 `KHR_gaussian_splatting` and the draft nested `KHR_gaussian_splatting_compression_spz_2` used by Cesium. Reject the removed original SPZ extension.
- Support explicit 3D Tiles trees, single GLB/glTF content per tile, and nested external tilesets. Diagnose implicit tiling and multiple contents. Standalone PLY/SPZ, reconstruction, upload, export, and tiling are deferred.
- Decode linear scales, normalized opacity, xyzw quaternions, and complete spherical harmonics through degree 3. Apply SPZ scale/opacity activations only to compressed data. Standards-based compressed content decodes in glTF's LUF coordinate system; the established Cesium draft profile preserves its stored convention.
- Support perspective and orthographic 3D views, view/branch clipping, opaque BIM occlusion, and model picking. Picking uses the nearest mean-plane fragment with Gaussian alpha at least 0.1; splats supply no measurement or snapping geometry.
- Blend in the declared trained color space before converting linear colors to display colors. Correct interleaving with translucent BIM and mixing differently trained color spaces are preview limitations.

## Implementation

1. Add `RenderSystem.Options.enableGaussianSplats` (`@alpha`, default false), internal splat data/geometry, and Display Test App configuration.
2. Add validated raw accessors and SPZ decoding in a bundled browser worker. Resolve external buffers through the reality data source so ion authentication follows the existing transport. Reject malformed or unsupported profiles with diagnostics.
3. Add a dedicated Gaussian render pass. Gather visible tiles across each viewport, retain high precision transforms relative to tile origins, globally radix-sort off the main thread, and draw projected covariance ellipses with spherical harmonics. Share paged GPU storage across viewports; release data as tile geometry expires and include allocations in memory accounting.
4. Integrate resolved opaque depth, logarithmic depth, clipping, and native pick attachments. Preserve the renderer's cached GL state. Coalesce camera updates and reject sort results for stale content generations.
5. Add offline decode and rendering fixtures, worker/lifetime tests, and a reproducible 1-million/4-million visible-splat benchmark. Compare a compatible live ion asset with CesiumJS 1.146 when credentials and hardware permit.

## Design findings during implementation

- **Dedicated blending pass:** iTwin.js's ordinary transparent pass uses weighted order-independent transparency. Gaussian splats require sorted alpha composition; they must render after opaque BIM in a separate pass and before ordinary translucency.
- **Shared GPU storage:** sorting independently within tiles produces overlap seams. A viewport-wide instance list can reference shared paged splat storage while carrying per-tile transforms, clip planes, and feature IDs. This also avoids duplicating splat textures across viewports.
- **Worker packaging:** the existing frontend worker build produces a self-contained classic script in `public/scripts`. The splat worker will use the same packaging and public-path conventions.
- **WASM worker URL:** the SPZ Emscripten glue uses `import.meta.url`. The classic-script build must replace it with `self.location.href`; Rollup's default IIFE replacement references `document.currentScript`, which fails in a worker. Golden decode tests caught this.
- **SPZ adapter:** `@spz-loader/core@0.3.1` already exponentiates scales and applies sigmoid to alpha. Request a DC color factor of 1, remove its 0.5 offset to recover SH coefficients, and apply no further scale/opacity activation. Validate this against a compressed golden fixture. Decode explicitly in LUF.
- **SPZ antialias flag:** preserve the decoder's training flag. Apply projected covariance determinant compensation when broadening antialiased splats with the pixel filter, rather than silently treating them as conventional splats.
- **Affine covariance and SH:** transform covariance with the full model-view linear transform. Evaluate SH using the camera-to-mean direction expressed in the original local coordinate system; this preserves directional lighting under node/tile rotations without rewriting SH coefficients.
- **Dependency setup blocker:** the first `rush update` reached an unrelated backend native postinstall and failed with registry authentication error E401. Frontend work continues with lifecycle scripts skipped; the full repository build may still need those credentials. This does not change the renderer architecture.
- The user refreshed VSTS authentication; retry the normal Rush installation before verification.
- **Dependency setup resolved:** normal `rush update --recheck` passed after the authentication refresh. `rush build --to @itwin/core-frontend` also passed for all 13 selected packages.
- **LOD readiness:** decoded content is committed only after the decode worker finishes. Retain one completed global field while the latest candidate selection awaits both native visible coverage and its sorting worker, then hand off the whole selection atomically. New multi-splat content becomes visible and pickable only after its global order is ready; a single splat has no ordering ambiguity. Initial content still needs its first sort and can build up progressively before the first complete source selection. This prevents a missing field during replacement sorting or partial reload; it does not crossfade changes in capture detail.
- **Residency:** share GPU pages selected or retained by at least one viewport. Charge cached tile CPU data and worst-case GPU page size to the existing tile-cache budget; separately account for completed-field geometry retained through a transition. One completed selection and one latest candidate can coexist in CPU, worker, and GPU storage. Tile-cache eviction does not dispose the completed field until its renderer leases are released. The atlas is capped by the device's array texture layer limit; exceeding it reports a diagnostic. An active source can retain its completed field through a temporary empty native selection; this is not an automatic active-splat budget.
- **Viewport state:** the native renderer shares one canvas across viewports. The dedicated pass sets and restores the GL viewport explicitly; framebuffer binding alone does not select the target's dimensions. Browser fixtures read the actual viewport center because frontend initialization can resize their container.

Pass unresolved relative buffer URIs to the loader and resolve them against the tile content's directory before using its existing data source. Absolute ion resources receive asset authorization only inside the endpoint's origin and path.
- **Multisampling:** custom draws bypass the native technique executor's dirty-buffer tracking. Mark the composite destination dirty and resolve its MS color attachment after the Gaussian pass; resolve opaque MS depth before testing Gaussian fragments.
- **Cesium SPZ convention:** CesiumJS 1.146's loader uses `UNSPECIFIED`, while the Khronos SPZ draft requires LUF. Its official `sh_unit_cube` fixture has the established draft's COLOR_0 placeholders, no degree-zero SH accessor, and no kernel/colorSpace fields. ### Closing the measured GPU gap

The 2026-10-08 source review prioritizes GPU draw work for the warm-frame gap. Native gathering/preparation is small in the recorded phase samples; atlas residency and sorted-instance remapping already have steady-state fast paths. Sorting and uploads remain important during navigation, but these settled measurements do not justify redesigning them first. GPU elapsed queries cover the whole frame, so they do not yet attribute time to splat shading versus composition.

Proceed one change at a time and measure the same tower and campus cameras after each, as requested by the user. Preserve actual submitted counts, readiness, framebuffer size, and reference settings. Keep each raw report separately, compare native images against the preceding step, and keep Cesium timings as a check on run-to-run conditions. Retain appearance-preserving changes when they help; treat quantization or culling-policy changes as visual experiments for the user's desktop review.

1. **Four-vertex triangle strip.** Native currently invokes the projection/covariance/SH shader six times per splat; Cesium uses four vertices for the same two triangles. A strip preserves native ellipse size, falloff, sorted order, and clipping/picking interpolation. It removes one third of vertex invocations, not necessarily one third of frame time. Even a completely vertex-bound frame has at most a 1.5× theoretical improvement from this change alone.
2. **Reduce repeated shader work.** At SH degree 3, `shFloat` expresses 48 scalar coefficient fetches from only 12 distinct RGBA texels per vertex. Explicit vector loads can avoid repeated addressing/fetch expressions while retaining every coefficient; the compiler may already eliminate some duplicates, so improvement must be measured. A color-only shader variant can also omit pick feature/depth outputs and unused clip varyings in unclipped views while retaining the full native pick/clip path. Drivers may already eliminate inactive output work; do not assume its source cost equals executed GPU work.
3. **Avoid pixels already discarded by the existing alpha rule.** The color pass rejects alpha below 1/255. Reject a whole splat when its effective peak alpha is below that threshold, and conservatively tighten its quad to radius `min(3, sqrt(2*ln(peakAlpha/threshold)))`. Use the same opacity, appearance, antialias compensation, and pixel-center coverage as the fragment calculation; picking has its own 0.1 threshold. This can preserve the current image without adopting Cesium's unconditional small-splat removal. Keep retained data and global sorted ordering intact.
4. **Reduce GPU storage bandwidth.** Native stores 240 bytes per splat even for lower SH degrees. The reference uses 32 bytes of packed position/covariance/color plus 8 bytes per higher SH coefficient: 152 bytes at degree 3, before texture padding. Explicit vector loads come before a storage redesign. Compact SH storage, potentially FP16, can improve cache density and uploads; preserve float32 relative means, double-precision placement, shared atlas leases, and atomic rollback. Quantization is lossy and covariance can overflow/underflow FP16, so range checks and a float32 path are required before changing supported input behavior. Memory figures from different renderers remain differently accounted.
5. **Experiment with an RGBA16F color field.** The native float path uses RGBA32F for blended splats and two full-screen initialization/composition passes per active color space; the recorded reference has HDR disabled and its scene framebuffer uses unsigned-byte color. A half-float field halves native attachment bytes per pixel while preserving floating-point range, but changes blend rounding and needs dense-overlap/HDR color checks. Measure the splat draw and composition separately before removing passes. The current Khronos draft defines a 3σ kernel and composition in the trained color space; float blending is recommended because intermediate colors are not bounded to [0,1]. Direct unsigned-byte rendering is a quality tradeoff, especially for linear trained-space data, rather than a blanket replacement for that contract.

**Footprint correction from tracing the full reference path:** [Cesium's companion WASM source](https://github.com/CesiumGS/cesium-wasm-utils/blob/96a2fbae7ab1d117dd533fe558f0e061bed6762b/wasm-splats/src/texture_gen.rs#L128), whose package version is the `0.1.0-alpha.2` dependency of CesiumJS 1.146, packs covariance multiplied by four. Its shader also uses full viewport focal terms and a different clip-space offset conversion. For the same covariance and perspective camera, ignoring size clamps/filter floors, the reference quad reaches roughly √8σ per axis versus native 3σ: the native bounding-quad area is approximately 9/8, or 12.5% larger. Comparing the shader constants alone would overstate this difference. After accounting for those factors, the reference's `+0.3` filter becomes approximately 0.01875 pixel² in the effective Gaussian covariance, versus native 0.3 pixel². It also rejects both projected axes below its cutoff and caps large axes. These are source-level explanations to test against tiny/large splat images, not measured attribution of the performance or brightness difference. Do not copy the center-only frustum rejection or small-splat cutoff unconditionally: broad ellipses and aggregate subpixel contributions can remain visible.

Broader quality policies, lower SH degree, looser LOD, GPU sorting, and changing the shared-canvas presentation architecture are deferred until the smaller experiments supply evidence. ### Hover locate and synchronous pick readback (2026-10-09)

For the graphics team. This is the largest remaining difference between iTwin.js and CesiumJS when navigating a Gaussian splat field with a mouse, and it is not splat-specific.

**Mechanism.** Every mouse motion event runs `AccuSnap.onMotion`, which calls `ElementPicker.doPick` → `Viewport.readPixels` → `Target.readPixels`. That re-renders the scene into the pick buffers for the cursor aperture and then calls `gl.readPixels` synchronously. `readPixels` cannot return until the GPU has executed every command queued before it, so it waits for all in-flight color frames plus the pick render. In a BIM scene the GPU is idle when the read arrives and the wait is near zero. A splat field costs 12–24 ms of GPU per frame at device pixels and redraws every frame during navigation, so the GPU runs one to two frames behind and each hover read stalls the main thread for 20–40 ms, up to 350 ms when a sort commit lands. Cesium's viewer picks only on click, never on motion, and its splat primitive skips the pick pass entirely, so it never pays this. Cesium does already have an asynchronous pick path (`PickFramebuffer.endAsync`, a pixel pack buffer polled with a fence) for explicit `pickAsync` calls.

**Measured** on the Redmond tileset (ion 4547222), 1440×900 at DPR 2 (2014×1510 canvas), M4 Pro, ANGLE Metal, 22 s of real pointer input (wheel zoom bursts with a moving cursor, a middle-drag pan, zoom back out, twice), other apps closed:

| Configuration | Main thread blocked in `readPixels` | Long tasks (count, total) | Frame interval p99 |
| --- | --- | --- | --- |
| Hover locate on, synchronous read, splat pick skipped while the cursor moves | 4.1–5.1 s | 23–25, 3.9–4.8 s | 167–200 ms |
| Hover locate stubbed out (only wheel/pan depth picks remain) | 0.5 s | 7–8, 0.7–0.9 s | 50–67 ms |
| Hover locate on, asynchronous read (prototype) | 0.16–0.19 s | 0 | 16.8 ms |
| CesiumJS 1.146 at device pixels, same route | 0 | 0 | 16.8 ms |

Hover locate reads were 152–166 per route; wheel-zoom depth picks (`pickDepthPoint`, 15 per route) and pan depth picks remain synchronous and account for the residual.

**Prototype** (this branch, internal, opt-in): `BatchState.snapshot()` captures the batch IDs of the pick render so they survive `resetBatchState`; `SceneCompositor.beginReadPixelsAsync` copies the depth/order and feature-ID attachments into `PIXEL_PACK_BUFFER`s with `readPixels(…, 0)`, places a `fenceSync`, and flushes; `Target.readPixelsAsync` renders exactly as `readPixels` does, starts that copy, releases the batch state, then polls `getSyncParameter(SYNC_STATUS)` every 2 ms and finishes with `getBufferSubData`, which does not stall once the fence has signaled. `Viewport.readPixelsAsync`, `ElementPicker.doPickAsync` and `AccuSnap.findHitsAsync` carry it to hover locate when `AccuSnap.asyncHoverReadback` is true. The synchronous path is unchanged and shares the render step.

**What a core change would involve.** The readback itself is small and shown above. The work is in the callers: `Viewport.readPixels` hands the buffer to a synchronous receiver and the tools layer assumes the result is immediate (`ElementPicker.doPick` returns a count; `AccuSnap.findHits`, `pickDepthPoint`, `ViewTool` collision picks, `ElementSetTool`, `queryVisibleFeatures`). Migrating hover locate alone, as the prototype does, is contained because `AccuSnap.onMotion` and `findLocatableHit` are already async and `ToolAdmin` serializes motion events, so later motion events wait for the pending read and coalesce. The wheel and pan depth picks would need the same treatment to remove the residual, and `ElementPicker` would need per-request state rather than one shared hit list if synchronous and asynchronous picks can interleave. Robustness items for a real implementation: a bounded number of in-flight reads, cancellation when the viewport changes or is disposed, pack-buffer support detection, and keeping `PIXEL_PACK_BUFFER` unbound outside the read so other `readPixels` callers are unaffected.

### Performance review findings (2026-10-09)

A code review against the Cesium target finds that the sort gap is mostly per-splat cost, not scheduling. Grouping the camera-run sorts by size gives about 50 ms per million splats (0.5M → 19 ms, 1M → 51 ms, 2M → 106 ms p50), against roughly 12 ms per million for the reference. A standalone Node reproduction of `sortGaussianSplats` on 2M synthetic splats (40 tiles, M4 Pro) takes 63.6 ms. A JS three-pass 11-bit radix sort over float32 camera distances, with reused scratch and output written in the final pass, takes 25.3 ms with no order inversions above 1 mm. A Cesium-style call with one concatenated buffer and one matrix takes 23.4 ms. The current worker allocates about 72 MB per 2M-splat sort, pads the WASM input with zero x/y, and runs two random-access passes (collision refinement, slot gather). Refinement is not visible at 2^28 bins.

Prioritized work:

1. Rewrite the worker sort as above. Pack each instance into one `uint32` (tile row plus tile-local index; the shader already has the tile's atlas base), which removes most remapping and halves transfer and `bufferData` volume.
2. Detail recovery required `hasSpareCapacity` (atlas below `budget / 4` = 64 MB). Both camera runs settled at 80 MB after the first memory-limit halving (at about 6.4 s, 1.34M splats), so detail never recovered. This likely explains most of the 1.03M versus 1.97M settled difference. The gate was the only safe threshold while a recovery step halved the tolerance (about 4x the splats) against a 128 MB steady-state limit. Replaced by `GaussianSplatAtlas.growthHeadroom`, which projects the admission checks for the resident selection, with the recovery step (2, √2 or 2^¼ on the tolerance, assuming inverse-square growth) chosen to fit it, and an exponential backoff (5 s to 60 s) when an attempted step is rejected. Measured at the detail pose (1440×900, DPR 2): the memory limit fires once during the fly-in (1.7M splats, 112 MB) and halves detail to 970k splats at 75 MB; the headroom-based recovery brings it back one quarter-octave to 1.13M at 88 MB, and stops there because full detail (Cesium selects 65 tiles, 1.85M splats, at the same SSE 16 and CSS size) would need about 148 MB at 80.7 bytes per splat against the 128 MB steady-state cap. The remaining gap is per-splat storage and the double-copy transition budget, not the recovery gate. Separately, packed tiles store float covariance and float appearance whenever any splat qualifies, which is effectively always for SPZ, so GPU storage is 80.7 bytes per splat versus 32. For SPZ, float appearance is coarser than the 8-bit source anyway.
3. The atlas rebuilt and re-uploaded every resident tile on each selection change (44 replacements, 810 ms, worst 165 ms). Residency is now incremental: persistent arrays with 1.5× spare capacity, first-fit page/row ranges per tile, rebuilds only on growth or when under half the capacity is in use, and in-place rebuilds when the replacement cannot sit beside the current arrays, which lifts the steady-state cap from half the budget to the whole budget. On the real-input route the atlas work fell to 25 calls, 204 ms total, with only the fly-in rebuilds above 10 ms. The detail pose now settles at 1.62M splats (151 MB) with a 1.9M peak, matching Cesium's selection, so per-frame sort and GPU work rise accordingly. A pick with an unchanged instance order no longer re-uploads the instance buffer twice. Still open: commit a completed sort for superseded content when all its tiles remain resident, instead of discarding 22–41% of sorts. Pacing on the scripted camera route (DPR 2, long tasks per 32 s run): 49/46/45 before, 30/0/63 and 3/61/25 after, so the median improved while one run in three stays poor. On the real-input route the atlas total fell from 272–476 ms to 175–204 ms, but GPU time stays near 45 ms per frame at p50, so that jank remains GPU-bound.
4. GPU: the fragment shader always writes `gl_FragDepth`, which disables early depth testing; compute depth per vertex instead, since each quad faces the camera. The field texture is RGBA32F; RGBA16F halves blend bandwidth. SH reads fetch a whole texel and the tile metadata for every coefficient.

Item 1 was tried and reverted. A sort rewrite (reused scratch, double-precision keys quantized to 32 bits, three stable 11/11/10-bit LSD radix passes writing slot and row in the final pass, no WASM) cut the isolated worker benchmark from 63.8 to 25.6 ms median for 2M splats in Chromium. Live navigation was worse, though. On the matched camera route at 1440×900 CSS pixels and DPR 2 (2014×1510 canvas), three runs each without the change gave long-task totals of 1.3/0.07/0.45 s and frame-interval p99 of 50/33/33 ms. With it, the totals were 3.2/3.3/2.1 s and p99 was 83/67/67 ms. The likely cause, not yet isolated: faster sorts let candidates commit more often, and each commit triggers a full atlas rebuild plus a full instance upload. Consistent with that, main-thread time blocked in the atlas `getError` doubled. The rewrite should only return once commits and residency are incremental, or result uploads are rate-limited.

A frame profile (CDP CPU sampling, per-frame `EXT_disjoint_timer_query_webgl2`, and per-enum `getParameter` timing) found the main thread blocked for 11.8 of 32 seconds in `gl.getParameter(gl.VIEWPORT)` inside `withGaussianSplatBindings`. That call synchronizes with the GPU process; the other state reads cost almost nothing. Removing it cut iTwin's per-route render CPU from about 16 to 6.4–7.9 s, but pacing did not improve: long tasks were 1.6/1.2/2.7 s and p99 50/50/67 ms. The waits moved to the next synchronizing calls (atlas `getError`, `texImage2D`, `bufferData`), so that change was also reverted. At Retina resolution the GPU is the bottleneck, and these synchronizing calls only decide where the wait appears. The timer queries include queueing, since even Cesium's totals exceed wall time, so treat them as relative only.

The harness compares unequal pixel counts. Cesium's default `useBrowserRecommendedResolution` renders at CSS pixels (a 1007×755 canvas at DPR 2), while iTwin renders at device pixels (2014×1510). At DPR 1 both use 1007×755 and iTwin's frame-interval p95 matches Cesium's 16.8 ms. Reducing GPU work per frame is the next priority: splat-field resolution on high-DPR displays, an RGBA16F field, depth computed per vertex instead of `gl_FragDepth`, smaller per-splat storage, and incremental atlas residency.

Retained GPU step: the splat field is now RGBA16F instead of RGBA32F (blending into it needs only `EXT_color_buffer_float`), and log depth is written per vertex instead of through `gl_FragDepth`. Each quad faces the camera at its mean's depth, so the depth is the same as before. Six alternating runs at DPR 2 (baseline/changed, matched p95 of 970,119 drawn splats) gave GPU-per-frame p95 of 53/57/58 → 47/50/52 ms and main-thread render p95 of 27–28 → 24–26 ms. Frame-interval p99 went 50/50/50 → 33/33/67 ms. This is a modest, consistent reduction that does not bring frames under budget. GPU p50 stays near 20 ms, and quadrupling the pixels earlier added only about 6 ms, so most GPU time scales with splats or other frame passes rather than pixels. Next, separate the splat pass's GPU time from the rest of the frame, and vertex cost from fragment cost, before choosing further changes.

With real pointer input (continuous mouse movement, wheel zoom, middle-drag pan; DPR 2), the jank reproduces: 20–43 frames over 50 ms, 2–13 over 100 ms, worst 283–317 ms, and 2.2–4.8 s of long tasks in about 24 s. The scripted camera route shows almost none of this. Hover picks occur in most slow frames (about 8 per second), but disabling splat pick rendering made jank worse (49/56 slow frames, 6.2–7.7 s of long tasks), so picks are not the cause. The slow frames are main-thread render calls of 40–90 ms that wait for the GPU.

Static-frame cost at a settled pose (renderFrame plus `gl.finish()`, medians, wide p10–p90 spread), detail pose with 970k splats: full frame 20.5 ms at DPR 2 and 16.9 ms at DPR 1; iTwin passes without splats 6.5–6.7 ms; splats scissored to one pixel 14.6–14.8 ms. Per-splat, resolution-independent work is therefore about 8 ms, fragments and blending about 6 ms at DPR 2, and iTwin's own passes about 6.5 ms. Removing the float covariance and appearance supplements, which skips their shader fetches, did not reduce cost (26.1 versus 22.7 ms full). This part of the vertex-cost hypothesis is unsupported, and the measurement noise is large. Per-splat GPU work needs a more precise tool, such as a Metal frame capture, before the next optimization is chosen.

Correctness: every pick uploads the full instance buffer and marks it dirty, so the next draw uploads it again, even when the pick reuses the committed array. Registration copies positions with one `subarray` per splat. Also check whether the whole-tree coverage gate is stricter than needed when native selection already substitutes parents for loading children. Rebuilding the SPZ codec's emscripten module for every `loadSpz` call, plus retiring the single decode worker whenever it goes idle, limits tile throughput.
